# M1: platform skeleton

**Status:** implemented. Acceptance is met both on envtest and on a real kind cell running Strimzi 1.3.0 (GitHub Actions, see [Results](#results)).

## Scope delivered

| Area | What exists |
|---|---|
| API (`internal/platform/api`, `api/openapi.yaml`) | `POST/GET /v1/clusters`, `GET/DELETE /v1/clusters/{id}`, `GET /v1/clusters/{id}/bootstrap-brokers`, `GET /v1/operations/{id}`. All mutations are async, require an `Idempotency-Key`, and return an `Operation`. A per-cluster lock gives 409 on concurrent mutations. A test keeps the OpenAPI spec and the served routes in sync (`openapi_test.go`). |
| Metadata (`internal/platform/store`) | PostgreSQL schema (goose migration `00001_init.sql`): tenants, cells, pools, per-zone capacity, reservations and items, clusters, append-only desired-state generations, observed status, operations, idempotency keys, outbox, audit log. |
| Workflows (`internal/platform/workflows`) | Temporal `CreateCluster` and `DeleteCluster`. Activities are idempotent; errors are split into terminal and retryable types; a failed create is compensated by a tombstone followed by `FAILED`. A transactional outbox starts workflows with workflow ID = operation ID. |
| Capacity (`internal/platform/capacity`) | The reservation is taken in one transaction under `FOR UPDATE` locks on per-(pool, zone) rows, taken in a fixed order. Free capacity is computed as the sum of active reservations, so there are no counters that can drift. Distinct-node feasibility is checked per pod group. A reservation is held, then committed or released; a heartbeat extends it and a sweeper releases expired ones. Operator-shard selection is included. |
| Cell agent (`internal/agent`) | Long-polls `/cell/v1/desired` and applies with server-side apply in bundle order. Pruning is scoped to the cluster's own objects. Tombstones carry object references, so deletion still works after the agent loses its local state. Status and heartbeat include node inventory. State is persisted in a ConfigMap. Safety rules: absence never deletes; a revision regression pauses the agent; a mass-delete brake holds large deletions. |
| Engine (`internal/platform/engine`, `internal/engines/kafka`) | An engine-neutral interface and registry. The Kafka engine provides validation (versions, sizes, broker count, storage, config allowlist), placement planning, and a deterministic Strimzi v1 render: Namespace, five NetworkPolicies, `Kafka` (tlsroute + internal mTLS listeners, rack awareness, PDB 0, Cruise Control auto-rebalance, User Operator), and controller and broker `KafkaNodePool`s with shared or dedicated placement constraints. `ObserveStatus` maps Strimzi status, including bootstrap endpoints. An architecture test fails if platform code imports an engine. |
| Local environment (`deploy/kind`) | A kind cell where node pools are simulated with labels and taints: 3 control workers (tainted) and 3 shared workers across zones a/b/c. It runs Strimzi 1.3.0 cluster-wide on shard 0, plus Envoy Gateway with a TLS-passthrough `Gateway`. `up.sh` starts the control plane on the host, `smoke.sh` runs the real-Strimzi acceptance, and `down.sh` tears everything down. |
| Binaries | `streamcell-api` (tenant API, cell API, outbox dispatcher, reservation sweeper), `streamcell-worker`, `streamcell-agent`, `streamcell-admin` (`register-cell` / `register-tenant`). |

## How acceptance is tested

`make e2e` runs these real components:
- PostgreSQL 17 (docker);
- a Temporal dev server (Temporal Server 1.32.2);
- a real `kube-apiserver` and etcd (envtest, Kubernetes 1.34.1) with the vendored Strimzi 1.3.0 CRDs installed. Every rendered object is therefore validated by Strimzi's own CRD schemas when the agent applies it.

The API, outbox, workflows (in a separate worker **process**), capacity and agent are all the production code.

envtest has no kubelet, scheduler, controller-manager or Strimzi operator. `test/e2e/sim_test.go` stands in for exactly two behaviours:
- it marks a `Kafka` resource Ready for its current generation and publishes the bootstrap address, as Strimzi's status does;
- it finalizes empty Terminating namespaces, as the namespace controller does.

It never creates or deletes platform objects. The real-Strimzi path is covered by `make kind-up kind-smoke`, which brings up 3 brokers and 3 controllers and checks their placement.

Crash testing: the worker is built with `-tags faultinject`. `STREAMCELL_FAULT_CRASH_AFTER=<point>` makes the worker process exit with code 137 immediately **after** an activity's side effects have committed and **before** Temporal records the activity as complete. This is the worst case for duplicate side effects: Temporal must re-run the activity. Each test asserts the exit code was 137, which proves the crash really happened at that point. It then restarts the worker and asserts each of these exists exactly once:
- the cluster row, operation, outbox entry and reservation;
- 6 reservation items (2 pools × 3 zones);
- one desired-state generation;
- cell revision bumps equal to the number of desired-state rows;
- one Namespace, one Kafka, two KafkaNodePools and five NetworkPolicies in the API server.

The roughly 10 s per crash case is the 4 s activity (or heartbeat) timeout after which Temporal retries on the restarted worker, plus process start-up.

Unit tests (`go test ./...`) pass: engine validation, render determinism and placement terms; OpenAPI validity, route parity and schema conformance; API request validation; the architecture rule.

Bugs found by these tests and fixed during M1:
1. **Capacity: the distinct-node check summed pods across groups.** Controllers and Cruise Control/Entity Operator in the same zone were treated as needing 2 nodes. The check is now per group.
2. **Agent: a nil dereference in resync** when a cluster finished deleting concurrently. Found by the mass-delete test.

So, with the real operator:
- the rendered `Kafka` and `KafkaNodePool` resources reconcile to Ready;
- the TLSRoutes are accepted by Envoy Gateway;
- the platform's default-deny NetworkPolicies still let the cluster form under kindnet;
- the worker kill mid-create left no duplicate rows;
- placement constraints hold on real scheduling.

This smoke test does not cover client connectivity. Producing and consuming through the gateway needs DNS, the cluster CA and SCRAM users, which are M3.

**Finding: deletion is slow (6m12s).** It is not fully diagnosed. The likely cause is that deleting the `Kafka` resource terminates brokers and controllers at the same time. The brokers then wait out their 300 s termination grace in a controlled shutdown that the departing controllers never acknowledge. Fix candidate for M4: delete the broker node pool first, wait for its pods to go, then delete the rest, or lower the grace period for deletes only.

## Deviations from the design, to close in later milestones

| Item | M1 state | Target |
|---|---|---|
| Tenant authentication | Static bearer tokens (`STREAMCELL_DEV_TOKENS`) | OIDC (M3) |
| Cell agent authentication | Per-cell bearer token, stored hashed | mTLS identity (M3) |
| Kafka authorization | `simple` (StandardAuthorizer) with platform super users | `PlatformAuthorizer` plugin (M3, ADR-0010) |
| Dedicated tier | Rendered and unit-tested; the API returns 422 | Capacity + Karpenter NodePool (M2) |
| Admission policy, binding webhook, auditor | Not yet | M2 |
| Secrets and SCRAM users | Not yet (no tenant users in M1) | M3 |
| Agent HA | Single replica; ConfigMap state with an optimistic-concurrency check | Leader election (M2/M3) |
| Pod Security | Namespace enforces `baseline`; warns and audits `restricted` | `restricted` after spike S-4 |
| sqlc, oapi-codegen | Not used; hand-written pgx queries and handlers, with an OpenAPI parity test | Revisit if the API grows |
| Audit-log immutability | Append-only by convention | DB role grants (no UPDATE/DELETE) at deployment |
