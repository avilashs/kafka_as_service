# M4: lifecycle operations

**Status:** config change, resize, version upgrade, scale out and scale in are implemented and verified on a real cell (kind, real Strimzi 1.3.0, real Cruise Control) **under continuous `acks=all` idempotent load, with a verifier that found 0 lost, 0 duplicated, 0 corrupt and 0 reordered acknowledged records in every operation**. Storage expansion is implemented and tested against the API and the cell objects only. Tier migration (spike S-6) and node rotation are **not** implemented; see [What is not done](#what-is-not-done-or-not-proven).

Acceptance (from the brief): *each operation under `acks=all` load with the verifier: 0 lost acknowledged messages.*

## Scope delivered

| Area | What exists |
|---|---|
| API | `PATCH /v1/clusters/{id}` with a JSON merge patch of `spec`; asynchronous, idempotent (a replay is answered before the patch is validated against state the first call changed). Operation types `ChangeConfig`, `ResizeCluster`, `ScaleCluster`, `ExpandStorage`, `UpgradeCluster`. |
| One kind per request | `engine.Changer.ClassifyChange` refuses a patch that changes nothing or mixes kinds (version, size, scale, storage, config), downgrades, storage shrink, tier changes, user changes. Each operation has one safety argument. |
| Capacity | `Allocator.ReserveChange` reserves the new spec's demand in the cluster's own cell without counting the cluster's current reservation against itself; on success the old reservation is released, on failure both stay accounted (over-counting is the safe direction). A change that cannot be placed restores the previous spec before anything is published (`RevertSpec`) and fails the operation terminally with the cluster untouched. |
| Workflow | `UpdateCluster` (prepare + reserve → publish generation → wait Ready → finish) under the per-resource lock. The update path now has crash tests at every activity boundary (an M3 gap). |
| "Ready" | The Kafka engine's `ObserveStatus` requires: the `Kafka` resource Ready for its generation; no auto-rebalance running; every node pool's `observedGeneration` caught up; and **the broker pods themselves converged**: exactly `brokerCount` of them, all Ready, none terminating, each with the broker type's memory limit and an image of the spec's Kafka version. A change must additionally hold for a stability window (config 20 s, size/storage/version 30 s, scale 90 s). |
| Load tool | `cmd/streamcell-loadtest` / `internal/loadgen`: N idempotent `acks=all` producers write `(producer, seq, sha256, payload)` records through the public endpoint (SCRAM + TLS, certificate verified against the broker's own name) and keep a ledger of acknowledged records; the verifier reads the whole topic and reports lost, duplicated, corrupt and reordered records. |
| kind cell | 6 shared nodes (2 per zone) so that 6 brokers run on 6 nodes; a second dev broker size (`dev.small`); derived images for Kafka 4.3.0 and 4.3.1. |

## Results

### 1. Real cell, real load (CI job `kind-real-strimzi`, scenario `lifecycle`, run 41944239017, commit `be39685`; all jobs green)

One shared cluster (`dev.tiny`, 3 brokers, Kafka 4.3.0), topic `load` (6 partitions, RF 3, `min.insync.replicas=2`), two producers at 150 records/s through the gateway on port 443. For each operation: start producing, wait 15 s, send the PATCH, wait for the operation, keep producing 15 s, stop, verify the whole topic against the ledger of that run.

| Operation | Operation time | Acked records | Producer failures | Lost | Duplicated | Corrupt | Reordered |
|---|---|---|---|---|---|---|---|
| baseline (nothing happens) | – | 3 008 | 0 | 0 | 0 | 0 | 0 |
| config change (`log.retention.hours` 168 → 48) | 142 s | 26 664 | 0 | 0 | 0 | 0 | 0 |
| resize `dev.tiny` → `dev.small` (rolling restart) | 147 s | 26 516 | 0 | 0 | 0 | 0 | 0 |
| version upgrade 4.3.0 → 4.3.1 (rolling restart) | 297 s | 49 204 | 0 | 0 | 0 | 0 | 0 |
| scale out 3 → 6 brokers | 419 s | 68 195 | 0 | 0 | 0 | 0 | 0 |
| scale in 6 → 3 brokers | 236 s | 40 774 | 0 | 0 | 0 | 0 | 0 |

Total: 214 361 records in the log, 214 361 acknowledged by the cluster. Further checks that passed: the new value is in the cell and visible through the Admin API; every broker pod has the new memory limit; every broker runs 4.3.1; after scale out 6 broker pods run on 6 distinct nodes and all 6 brokers hold replicas of the load topic (the rebalance moved data); after scale in 3 pods and 3 brokers hold replicas; no under-replicated partitions after any operation (polled for up to 3 minutes); the cluster is ACTIVE after each; downgrade and storage shrink are refused with 422; delete works (61 s).

The verifier is not vacuous: `internal/loadgen` has an integration test against a real Kafka that makes it report a lost record, a duplicate and a corrupted record, and checks the TLS+SCRAM relay path (and that a wrong CA fails).

### 1b. The earlier scenarios on the M4 code

The M4 changes touch cluster creation too (the pod-based readiness gate applies to every cluster), so the M1–M3 scenarios were run again on the same code (run 41944238126, commit `be39685`): **dedicated PASS, shared PASS**; the M3 connectivity scenario had **one transient failure**: right after the clusters were ACTIVE, `kafka-topics --create` failed with `No subject alternative DNS name matching b0.<cluster>… found` (the connection to a per-broker name reached a TLS server whose certificate lacked that name); the checks that do not need that name passed, the later transactional and consumer-group checks passed, and everything that depended on the topic that could not be created failed with it. Re-run on commit `5282124` (run 41955765407, which retries the topic creation and reports the wait): **connect PASS, 50 checks, 0 failures, per-broker names reachable 3 s after the first bootstrap**. I did not reproduce the failure and have no explanation. The candidates are the Gateway data plane (per-broker `TLSRoute`s not yet programmed when the cluster turns ACTIVE) or Strimzi issuing a certificate before the route hostnames were known. Either way it says the same thing: **ACTIVE does not yet imply reachable through the public endpoint**; the design's per-cluster canary (M5) is the thing that should define that, and until it exists a client must retry.

### 2. envtest suite

`go test -race -tags e2e ./test/e2e/` passes, including: `TestM4ChangeValidation` (13 refused requests create no operation; no key, unknown field, other tenant, concurrent change → 409, replay, null removes a config key), `TestM4LifecycleOperations` (config, storage, size, scale out and in with the reservation replaced each time, a change that cannot be placed leaves the cluster as it was), `TestM4VersionUpgrade`, and `TestM4WorkerCrashDuringScale` (the worker is killed after each of six points of an update; exactly one more desired-state row, one active reservation of the right size, none left HELD, the right replica count in the cell).

Unit tests: `ClassifyChange`, the `ObserveStatus` gates, `brokerPodsConverged` (six ways to be unconverged), merge patch.

### How it got here (runs 19–23, kept because the failures were informative)

| Run | Finding |
|---|---|
| lifecycle 1 | The script died at the first `grep` without a match under `set -e` (my script). |
| lifecycle 2 | Zero loss for the baseline and the config change; **a resize "finished" in 5 s with brokers on mixed memory limits**. A resize changes only the `KafkaNodePool`, the `Kafka` resource's generation does not move, so my readiness check (written for M1) passed at once. The run then hung for two hours: the verifier and the producer's shutdown waited without bounds while brokers were rolling. |
| lifecycle 3 | Gate on the node pool's `observedGeneration`: **not enough**. Strimzi sets it early. Resize "took" 5 s again, scale out 10 s with only 3 brokers holding replicas. (Zero loss in every operation even so.) |
| lifecycle 4 | Gate on the pods themselves + a stability window: the durations above, and every check passes. |

The lesson is general: an operator's status says what the operator knows at the moment it last wrote it. "Done" for a change that rolls pods is judged by looking at the pods.

## Decisions taken

- Merge-patch `PATCH`, one kind of change per request.
- Version upgrades are patch upgrades only (4.3.0 → 4.3.1): the only supported versions are 4.3.0 and 4.3.1, which share a metadata version. The two-phase minor upgrade (roll, soak, then finalize `metadataVersion`) is designed (§16) but cannot be exercised until a second minor version is offered.
- A failed update leaves the new spec as the desired state (the operator keeps working on it) and reports the failure on the operation; a change that was never published (no capacity) is reverted.
- Storage shrink is refused; local-NVMe ↔ network-volume size changes are refused (they need node rotation).

## What is not done or not proven

1. **Storage expansion on a real cell.** Kind's `standard` StorageClass (local-path) cannot resize volumes. The API, the validation, the rendered `KafkaNodePool` storage and the accounting are tested in envtest; whether the EBS CSI driver and Strimzi grow the volumes online is for M6. Auto-expansion by the agent (design §13) is not built.
2. **Tier migration, spike S-6: not implemented, not tested.** What can be said from the vendored CRDs only (the Strimzi documentation host was not reachable from this session, so nothing below was checked against the documentation): listeners are configured on the `Kafka` resource, not per node pool, and a `KafkaNodePool` has only `jvmOptions, replicas, resources, roles, storage, template`; so the two-pool migration (add a pool with dedicated placement, `remove-brokers` rebalance off the shared pool, delete it) is expressible with Strimzi's own primitives, and bootstrap names can stay if the listener hosts do. What it would need on our side that does not exist yet: a rendering with two broker pools at once, a reservation and node-pool claim for the dedicated side before anything is published, an admission policy that tolerates a cluster holding pods of both placements for a while, and a changed `tier`. On AWS the dedicated tier uses its own network path (ADR-0006), where mixed exposure needs two listeners and a roll: the risk named in the design stands. No result on feasibility is claimed.
3. **Node rotation** (EBS: Drain Cleaner; NVMe: surge broker + `remove-brokers`). Needs real node replacement and volumes that follow pods; kind's local-path volumes are bound to their node. M6 on AWS.
4. **Scale-in pre-check by projected disk use** needs broker metrics (M5). Today scale in relies on Strimzi: it empties the brokers by auto-rebalance before removing them, and the run shows it doing so under load.
5. **Operator upgrade**, **spike S-5** (ext4 reserved blocks on EBS): not started (AWS, M6).
6. **The stability window is a heuristic.** It bounds how long a just-turned-true status is believed; the verifier, not the window, is the proof. A rebalance that starts later than 90 s after the pods are ready would still be missed by the gate (the data-plane check after scale out would show it).
7. **One topology, one size family.** Everything above ran with `dev.tiny`/`dev.small` brokers on a 6-node kind cell at 300 records/s; no claim about throughput, latency or behaviour at production sizes. Producers saw no errors during rolls at this load; that is not a promise for other loads.
8. **Open from M3, still open:** OIDC for the tenant API (static dev tokens), the cluster-wide partition limit, `readOnlyRootFilesystem`, the 120–180 s delete time with its unexplained namespace-controller cause, whether the User Operator removes tenant-created ACLs over time.

make test e2e                      # unit + envtest (incl. the crash tests)

make kind-up && deploy/kind/smoke.sh lifecycle   # needs docker, kind, kubectl, helm, jq, openssl
