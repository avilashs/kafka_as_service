# M6: AWS hardening

**Status: partly done, and the part the brief asks for is NOT done.** The acceptance for M6 is *written results, measured on AWS*, for broker kill, node termination, zone outage (NACL-based zone isolation), disk full, control plane down, the noisy-neighbour OpenMessaging Benchmark comparison, and dedicated versus shared. **None of these has been measured on AWS**: the AWS runs were not approved yet (no spend, by your decision), and nothing in this milestone has touched AWS. What exists:

1. four of the seven tests **emulated on the kind cell**, with real Strimzi and real Kafka, under `acks=all` load and the verifier, with results below (they are emulations: the table says what each one does and does not show);
2. everything needed to run them on AWS **prepared offline**: OpenTofu for the cell, add-on manifests, a bootstrap script, AWS fault helpers, the benchmark configuration. It is **validated only syntactically** (below) and has never been applied.

## Results: the emulations on the kind cell

CI job `kind-real-strimzi`, scenario `chaos`, run three times with the same result: run 43669763190 (commit `92eab44`, with a disk-full step that did nothing, see its row) run 43673575365 (commit `6df208e`) and the final run 43675451032 (commit `2218096`, where every fault starts from a verified `ACTIVE` cluster); all green. The numbers below are from the first run, the second run's differences are named in the text under the table. One shared cluster (`dev.tiny`, 3 brokers, Kafka 4.3.1, topic with 6 partitions, RF 3, `min.insync.replicas=2`), two producers at 150 records/s through the gateway, `acks=all` and idempotence. For every fault: start producing, 20 s of steady state, inject, recover, keep producing, stop, verify the whole topic against the ledger of acknowledged records. Thresholds of the cell are shortened (broker down 60 s, health window 90 s).

| Test of the brief | What the kind run does | Not shown by it | Time to recovery (fault → all brokers Ready) | Acknowledged records lost / duplicated / corrupt / reordered | Cluster state |
|---|---|---|---|---|---|
| Broker kill | SIGKILL of one broker pod (grace period 0) | – | 30 s; no under-replicated partitions 5 s later | 0 / 0 / 0 / 0 (10 468 acked, 0 producer failures) | stayed `ACTIVE`; `ACTIVE` 52 s after the fault |
| Node termination | the node of one broker stopped for about 90 s (its container) and started again | on kind the volume is local to the node, so the broker could **not** be moved to another node; on AWS the EBS volume follows the pod. Replacement of a terminated node by Karpenter is untested | 112 s | 0 / 0 / 0 / 0 (23 230 acked, 0 failures) | `DEGRADED` after 51 s (canary 94.9 %, broker pod not ready), `ACTIVE` 137 s after the fault |
| Zone outage | every node of one zone stopped (one broker, one controller, a control-pool node) for about 90 s | no NACL: **nothing was dropped on the network**, the machines stopped. The gateway is one Envoy on kind, so the zone without it was chosen; on AWS there are three. Operator and webhooks ran on the control pool in the surviving zones | 103 s | 0 / 0 / 0 / 0 (21 645 acked, 0 failures) | `DEGRADED` after 35 s, `ACTIVE` 136 s after the fault |
| Control plane down | API, worker, Temporal and Postgres frozen for about 2 minutes, **and a broker killed meanwhile** | the central control plane is a host process here, not a cell | the broker came back 28 s later **with the control plane frozen** | 0 / 0 / 0 / 0 (18 478 acked, 0 failures) | `ACTIVE` 106 s after the fault; the tenant API did not answer meanwhile, as injected |
| Disk full | **not run.** The scenario has the fault (fill the broker's data directory, watch the broker, free the space as the runbook says), but kind's local-path volumes have no size limit: they live on the node's disk, which on the CI runner is the runner's disk. A first attempt filled it and killed the CI job (exit 137); the scenario now refuses to run the fault on a volume larger than 20 GiB and reports `SKIP`. (A still earlier run reported PASS for this fault, but the directory it meant to fill did not exist, so nothing had been filled: that PASS meant nothing and was removed.) | everything: what Kafka does on a full log directory, how long recovery takes, whether the runbook's first step works | – | – | – |
| Noisy neighbour (OMB), dedicated versus shared | **not run, no emulation**: needs real instances and noisy-neighbour contention that kind cannot reproduce | everything | – | – | – |

The second run (43673575365) in the same order: broker kill ready in 29 s and `ACTIVE` 50 s after the fault, 10 230 acked, 0 lost; node stop `DEGRADED` after 25 s, ready after 90 s, `ACTIVE` 146 s after the fault, 23 196 acked, 0 lost; zone stop: 10 644 acked, 0 lost, but the cluster was **still `DEGRADED` from the previous fault when this one started** ("0 s"), so that run says nothing about detection time for the zone fault (the first run's 35 s does), and it took 250 s to be `ACTIVE` again; control plane down: the broker came back after 29 s with the control plane frozen, 18 474 acked, 0 lost, `ACTIVE` 105 s after the fault. The scenario did not wait for `ACTIVE` before the next fault; that was a defect of the test, not of the cluster, and is fixed. **Final run (43675451032):** broker kill `ACTIVE` 48 s after the fault, 9 988 acked, 0 lost; node stop `DEGRADED` after 25 s, `ACTIVE` 129 s after the fault, 19 044 acked, 0 lost; zone stop `DEGRADED` after 20 s (from an `ACTIVE` start), `ACTIVE` 138 s after the fault, 18 954 acked, 0 lost; control plane down: broker back after 28 s with the control plane frozen, `ACTIVE` 103 s after the fault, 0 lost; disk full `SKIP`.

Reading the table honestly: every kind of fault was survived with zero loss, which is what RF 3, `min.insync.replicas` 2 and `acks=all` are for, and the platform's own parts did their jobs (the canary and the health evaluator named the node/zone outages `DEGRADED` within a minute; the data plane repaired itself without the control plane). What kind cannot say: whether volumes follow pods across nodes and zones (EBS), whether Karpenter replaces a terminated node, how the NLB and three Envoys behave when a zone's network is cut, and anything about performance.

## What is not done or not proven

1. **All real-AWS results** (above). The IaC and the add-on script are untested against AWS. Expect problems in the first apply: IAM edges (Karpenter v1 policies are vendored from the upstream template, the cluster uses API authentication mode and Pod Identity, a combination I have not seen run), EKS add-on conflicts, the Gateway chart's value names, subnet tagging for the load balancers.
2. **Noisy-neighbour OMB comparison and dedicated versus shared**: prepared, not run. The shared-tier CPU model of ADR-0009 stays undecided: it is decided by that experiment.
3. **CNI**: the design names Cilium (Bandwidth Manager for `egress-bandwidth` shaping, a possible Cilium-based NetworkPolicy). The prepared cell uses the **VPC CNI with its NetworkPolicy support** (fewer parts, Apache-2.0); whether it enforces the platform's policies the way kind's CNI does is unverified (the kind isolation checks would have to be re-run on it), and the per-pod bandwidth annotation is not supported by this choice as far as I know. The ENI-versus-overlay decision the design left for M6 is therefore *not made on evidence*.
4. **Spikes not run** (they need AWS): S-5 (EBS ext4 reserved blocks, `tune2fs -m 0`), S-8 (local NVMe provisioner under Karpenter), S-9 (PrivateLink with per-broker ports and private DNS), S-2 (Strimzi shard size). **S-6 (online shared → dedicated migration) is not done** either; the M4 analysis from the CRDs stands, no experiment was run.
5. **Storage expansion on EBS and node rotation** (open since M4): not run.
6. **PrivateLink / dedicated-tier network path** (ADR-0006): no IaC written.
7. **The control plane's own deployment** (API, worker, Postgres, Temporal, OpenBao) is not part of the AWS code: the tests run it where the tests run, as on kind.
8. **Instance figures in `up.sh`** (vCPU, memory, EBS bandwidth, attach limits of `m7i.*`) are written from memory and must be re-verified against the EC2 documentation before the allocator is trusted with them.
9. **Open from earlier milestones, still open:** OIDC for the tenant API, the cluster-wide partition limit, `readOnlyRootFilesystem`, the 120–180 s delete time (181 s in the chaos run), whether the User Operator removes tenant-created ACLs.

## What a real AWS run would cost

A rough estimate (us-east-1 on-demand prices from memory, to be re-checked; **not a quote**): the always-on part of a cell (EKS control plane, three NAT gateways, NLB, three `m7i.large` control nodes) is about $0.6/hour; a shared pool of six `m7i.2xlarge` adds about $2.4/hour, a dedicated pool of three to nine `m7i.xlarge` $0.6–1.8/hour, benchmark workers (three `c7i.2xlarge`) about $1/hour. Cross-zone replication traffic ($0.01/GB each way) is the item that can surprise: the benchmark at 30 MB/s with RF 3 moves about 60 MB/s between zones, roughly $4/hour, and the noisy workload far more. A time-boxed window of 8 hours is therefore in the **low hundreds of USD**, and a repeat of failed tests doubles it. Everything would be destroyed with `tofu destroy` at the end; NAT gateways, EBS volumes and the NLB are what keep costing if something is forgotten.
