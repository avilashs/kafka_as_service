# M6: hardening on a cloud (Azure)

**Status: partly done, and the part the brief asks for is NOT done.** The acceptance for M6 is *written results, measured on a real cloud*, for broker kill, node termination, zone outage (network-rule-based zone isolation), disk full, control plane down, the noisy-neighbour OpenMessaging Benchmark comparison, and dedicated versus shared. **The cloud for these runs is Azure, at your instruction (the brief named AWS first; [ADR-0019](../adr/0019-azure-for-m6.md)).** **None of the tests has been measured on Azure**: nothing in this milestone has touched Azure (this session has no Azure credentials, the network policy blocks the Azure management hosts, and no spend was approved). What exists:

1. four of the seven tests **emulated on the kind cell**, with real Strimzi and real Kafka, under `acks=all` load and the verifier, with results below (they are emulations: the table says what each one does and does not show);
2. everything needed to run them on Azure **prepared offline**: OpenTofu for the cell, add-on manifests, a bootstrap script, Azure fault helpers, the benchmark configuration. It is **validated only syntactically** (below) and has never been applied.

An earlier version of this milestone prepared the same for AWS (commit `9959a1d`); that code was removed from the tree when the target changed. Its cloud-neutral parts stayed (cert-manager webhook certificates, the alert, the benchmark configuration, the Karpenter provider).

## Results: the emulations on the kind cell

CI job `kind-real-strimzi`, scenario `chaos`, run three times with the same result: run 43669763190 (commit `92eab44`, with a disk-full step that did nothing, see its row) run 43673575365 (commit `6df208e`) and the final run 43675451032 (commit `2218096`, where every fault starts from a verified `ACTIVE` cluster); all green. The numbers below are from the first run, the second run's differences are named in the text under the table. One shared cluster (`dev.tiny`, 3 brokers, Kafka 4.3.1, topic with 6 partitions, RF 3, `min.insync.replicas=2`), two producers at 150 records/s through the gateway, `acks=all` and idempotence. For every fault: start producing, 20 s of steady state, inject, recover, keep producing, stop, verify the whole topic against the ledger of acknowledged records. Thresholds of the cell are shortened (broker down 60 s, health window 90 s).

|---|---|---|---|---|---|
| Broker kill | SIGKILL of one broker pod (grace period 0) | – | 30 s; no under-replicated partitions 5 s later | 0 / 0 / 0 / 0 (10 468 acked, 0 producer failures) | stayed `ACTIVE`; `ACTIVE` 52 s after the fault |
| Node termination | the node of one broker stopped for about 90 s (its container) and started again | on kind the volume is local to the node, so the broker could **not** be moved to another node; on Azure the managed disk follows the pod. The second run (43673575365) in the same order: broker kill ready in 29 s and `ACTIVE` 50 s after the fault, 10 230 acked, 0 lost; node stop `DEGRADED` after 25 s, ready after 90 s, `ACTIVE` 146 s after the fault, 23 196 acked, 0 lost; zone stop: 10 644 acked, 0 lost, but the cluster was **still `DEGRADED` from the previous fault when this one started** ("0 s"), so that run says nothing about detection time for the zone fault (the first run's 35 s does), and it took 250 s to be `ACTIVE` again; control plane down: the broker came back after 29 s with the control plane frozen, 18 474 acked, 0 lost, `ACTIVE` 105 s after the fault. The scenario did not wait for `ACTIVE` before the next fault; that was a defect of the test, not of the cluster, and is fixed. **Final run (43675451032):** broker kill `ACTIVE` 48 s after the fault, 9 988 acked, 0 lost; node stop `DEGRADED` after 25 s, `ACTIVE` 129 s after the fault, 19 044 acked, 0 lost; zone stop `DEGRADED` after 20 s (from an `ACTIVE` start), `ACTIVE` 138 s after the fault, 18 954 acked, 0 lost; control plane down: broker back after 28 s with the control plane frozen, `ACTIVE` 103 s after the fault, 0 lost; disk full `SKIP`.

Reading the table honestly: every kind of fault was survived with zero loss, which is what RF 3, `min.insync.replicas` 2 and `acks=all` are for, and the platform's own parts did their jobs (the canary and the health evaluator named the node/zone outages `DEGRADED` within a minute; the data plane repaired itself without the control plane). What kind cannot say: whether volumes follow pods across nodes and zones (a cloud disk), whether Karpenter replaces a terminated node, how the NLB and three Envoys behave when a zone's network is cut, and anything about performance.

## What is not done or not proven

1. **All real-cloud results** (above). The IaC and the add-on script are untested against Azure. Expect problems in the first apply: role assignments (the cluster identity's rights on the disk encryption set are a guess: Contributor on the set), quota (see the cost section), AKS options that conflict with each other (a custom network with a NAT gateway per subnet and `userAssignedNATGateway`, Node Auto Provisioning with the overlay network), the Gateway chart's value names, and the `AKSNodeClass` fields.
2. **Dedicated clusters through Node Auto Provisioning land in whichever subnet the node class names**, which the prepared `AKSNodeClass` does not set: they would not sit behind a zone's NSG, so the **zone-isolation test does not cover the dedicated tier** until the node class is pinned to the zone subnets.
3. **Noisy-neighbour OMB comparison and dedicated versus shared**: prepared, not run. The shared-tier CPU model of ADR-0009 stays undecided: it is decided by that experiment.
4. **No per-zone DNS names for the load balancer.** The AWS design (ADR-0005) gives each broker a name that resolves to the NLB's zonal address so that a client is served in its zone. Azure's Standard load balancer has one zone-redundant frontend here; the zonal-routing idea is not carried over, and the cross-zone cost question it answered is different on Azure (see the cost section).
5. **Spikes not run** (they need a cloud): S-5 (ext4 reserved blocks on a managed disk), S-8 (local NVMe: Azure's `Lsv3`/`Lasv3` sizes would be the analogue; no provisioner chosen), S-9 (Private Link with per-broker ports and private DNS), S-2 (Strimzi shard size). **S-6 (online shared → dedicated migration) is not done** either; the M4 analysis from the CRDs stands, no experiment was run.
6. **Storage expansion on a managed disk and node rotation** (open since M4): not run.
7. **The dedicated tier's private network path** (ADR-0006, AWS PrivateLink in the design): no Azure Private Link code written.
8. **The control plane's own deployment** (API, worker, Postgres, Temporal, OpenBao) is not part of the cloud code: the tests run it where the tests run, as on kind.
9. **VM size figures in `up.sh`** (allocatable CPU and memory, disk throughput and attach limits of the `Standard_D*ds_v5` sizes) are written from memory and must be re-verified against the Azure documentation before the allocator is trusted with them.
10. **Open from earlier milestones, still open:** OIDC for the tenant API, the cluster-wide partition limit, `readOnlyRootFilesystem`, the 120–180 s delete time (181 s in the chaos run), whether the User Operator removes tenant-created ACLs.

## What a real Azure run would cost

A rough estimate (pay-as-you-go prices for a US region from memory, to be re-checked; **not a quote**): AKS Standard tier $0.10/hour; three system and three control nodes (`Standard_D2ds_v5`, about $0.11/hour each) about $0.7/hour; four NAT gateways about $0.2/hour plus data processing; the load balancer a few cents. A shared pool of three to nine `Standard_D8ds_v5` (about $0.45/hour each) adds $1.4–4.1/hour, a dedicated pool of three to nine `Standard_D4ds_v5` (about $0.23/hour) $0.7–2.0/hour, three benchmark workers about $1/hour. Premium SSD volumes are small money for a day. **Traffic between zones inside a region was, to my knowledge, not billed on Azure** at the time of writing (a charge announced in 2022 was postponed); this must be checked, because it is what made the AWS estimate uncertain. That puts a time-boxed window of 8 hours at **roughly $50–150**, with a repeat of failed tests doubling it. The binding constraint is more likely **quota**: a new subscription's default regional and per-family vCPU limits are far below the roughly 150 vCPUs the full benchmark needs, and a quota increase takes time. Everything is destroyed with `tofu destroy`; NAT gateways, public IPs, disks and the load balancer keep costing if something is forgotten.
