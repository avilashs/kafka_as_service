# M5: observability and metering

**Status:** implemented and verified. On a real cell (kind, real Strimzi 1.3.0, real Kafka 4.3.x) the canary detects two injected outages and the cluster goes `DEGRADED` and back to `ACTIVE`; metering of a live cluster matches an independently sampled timeline across a frozen control plane and an agent restart. Several parts of the brief's observability stack are **not built** (see [What is not done](#what-is-not-done-or-not-proven)). The last full CI run on the final commit is green.

Acceptance (from the brief): *the canary detects an injected outage; metering reconciles under retries.*

## Scope delivered

| Area | What exists |
|---|---|
| Metering core | `internal/metering`: integer accounting (gauges in broker-seconds and GiB-seconds, counters from deltas with reset handling), 5-minute intervals in the kind cell (hourly in production), exact split at interval boundaries, `MaxGap` bound, `Close` on delete, `record_id = sha256(cell, cluster, meter, labels, interval_start, interval_end, schema)` that never covers the quantity ([ADR-0017](../adr/0017-metering-idempotency.md)). |
| Delivery | Agent: samples pods, PVCs and broker metrics; WAL spool on disk; `POST /cell/v1/metering` returns the stored IDs; the control plane inserts with `ON CONFLICT DO NOTHING` and records a different quantity for an existing ID in `metering_conflicts`. Migrations `00003_metering`, `00004_health`. |
| Meters | `broker_hours{size}`, `storage_gb_hours`, `data_in_bytes`, `data_out_bytes` (per broker; the platform's own canary topic is excluded). `privatelink_bytes` is not built. |
| Broker metrics | Strimzi Metrics Reporter on port 9404 with an allow list; reachable only from the cell's Prometheus and, for the agent's pod-proxy scrapes, the API server (`allow-metrics-ingress`). |
| Canary | `cmd/streamcell-canary`, `internal/canary`: per cluster a `platform-canary` SCRAM super user, topic `__platform_canary` (one partition per broker, RF 3, `min.insync.replicas` 2), `acks=all` produce through the **public** endpoint, consume and match by id; availability and p99 reported every 10–15 s. Clients are recreated every 2 minutes so that new connections (route, TLS, SCRAM) are exercised too. |
| Health | `internal/platform/health`: `DEGRADED` when canary availability over the window is below the threshold (production: 99 % over 5 minutes), when brokers are down for longer than a duration (5 min), or when under-min-ISR partitions persist (2 min); back to `ACTIVE` when the signals clear. Clusters in an operation or with stale observations are not judged. Every transition is audited. |
| Alerts | `deploy/alerts/kafka.rules.yaml` (broker metrics down, under-min-ISR, under-replicated, offline partitions) with four runbooks; a unit test fails the build if an alert lacks a runbook, a severity or points to an unknown placement rule; `make check-alerts` runs `promtool`. |
| kind cell | Prometheus in `streamcell-monitoring` with the rule files; a supervised gateway relay; the canary as a host process; 12 nodes. |

## Results

### 1. Real cell (CI job `kind-real-strimzi`, scenario `observe`, run 42023370151, commit `1a7dc22`: all checks pass)

One shared cluster (`dev.tiny`, 3 brokers). Thresholds are shortened for the kind cell: health window 90 s, availability threshold 95 % (one failed round is 3 of ~110 attempts; in production the window is 5 minutes and the threshold 99 %), broker down 60 s, round every 2 s, 5-minute metering intervals.

| Check | Result |
|---|---|
| Canary on a healthy cluster, through the public endpoint | 45 of 45 round trips; cluster stays `ACTIVE` |
| Prometheus | scrapes all 6 Kafka pods; `kafka_server_replicamanager_underminisrpartitioncount` is exported and 0; 8 alerting rules loaded, none firing on a healthy cluster |
| Metrics port 9404 from a pod outside the tenant namespaces | refused |
| **Outage 1: the gateway's NetworkPolicy removed** | `DEGRADED` **30 s** after the cut (canary availability 92.1 %, 105 of 114), reason names the canary; a stock Kafka client really cannot connect meanwhile; `ACTIVE` again 95 s after the policy was restored; the client connects again |
| **Outage 2: a broker lost for good** (node cordoned, pod deleted) | `DEGRADED` 75 s later, reason "2 of 3 broker pods are ready (not ready: …)"; clients still work with one broker down (RF 3, min ISR 2); `ACTIVE` again 40 s after the broker returned |
| Duplicates / conflicts | none, with the control plane frozen for 60 s (`SIGSTOP`) and the agent killed and restarted meanwhile |
| `broker_hours` | stored 890 / 820 vs a timeline sampled by the script itself every 5 s: 830 / 785 (tolerance: two sampling periods of 3 brokers plus 5 %). The interval in which a broker was lost is among those checked |
| `storage_gb_hours` | matches the timeline for every checked interval |
| `data_in_bytes` | 2 225 618 bytes stored for 4 000 produced records of 400 value bytes (1 600 000); the canary's own traffic is excluded |

### 3. Tests that do not need a cell

- Metering: unit tests (exact boundary split, counters and resets, gaps, restart equivalence, spool) and an envtest suite with an independent oracle under duplicate deliveries, agent restarts and a failing control plane (`go test -race -tags e2e ./test/e2e/`, 0 data races).
- Health evaluator: envtest with a controllable clock (durations, recovery, flaky path that stays above the threshold, a window with only failed probes, operations in progress, other cells' reports dropped, impossible reports dropped).
- Canary: `go test -tags e2e ./internal/canary` against a real Kafka (docker): healthy, then `docker pause` (an injected outage that keeps the sockets open), failures reported, healthy again after unpausing, and a second canary on the existing topic. Run repeatedly with `-race`.
- Alerts: `make check-alerts` (promtool and the runbook lint).

### How it got here (runs on the kind cell, kept because the failures were informative)

| Finding | Where it came from | Fix |
|---|---|---|
| **Strimzi's generated NetworkPolicies open the metrics port 9404 to every pod in the cell** (and would leak topic names through the metrics). | observe check "a pod outside the tenant namespaces CAN open 9404" | `STRIMZI_NETWORK_POLICY_GENERATION=false` on the operator, plus an explicit `allow-operator-ingress` policy. Isolation checks of M3 re-run green. |
| Canary: **0 of 42 round trips on a healthy cluster, and no log line saying why.** Failures were logged at debug. | first observe run | failures are logged at WARN (rate limited); the cause was `TOPIC_ALREADY_EXISTS` returned as the call's *error* by franz-go's admin client after a reconnect, which my code took for a failure, for ever. A test now starts a second canary on an existing topic. |
| Canary round hung for the whole test on a frozen broker (`ProduceSync` does not return when its context ends once the request is in flight). | repeated runs of the docker test (flaky 2 in 4) | the round waits for the produce only until its own deadline and drops the clients; a data race on the client field found by `-race` fixed. |
| **A removed NetworkPolicy does not break established connections** (conntrack), so a long-lived canary connection never noticed the "cut". | observe: no `DEGRADED` after 240 s | the canary recreates its clients every 2 minutes (20 s in kind). |
| **A canary target that disappears when the cluster's latest observation has no endpoint hides the outage.** | observe: no canary results at all during the cut | the control plane keeps the last complete target of every serving cluster. |
| A window of only failed probes never reaches `MinAttempts` because each failed round takes its timeout (15 attempts in 90 s). | observe | a window without a single success is judged from 6 attempts. |
| The canary's fresh consumer, positioned "at the end", missed the first round after each reconnect (about 1 round in 15). | observe: 93 % on a healthy cluster | the consumer starts two seconds back. |
| Metric names: `kafka_server_brokertopicmetrics_bytesin_total` does not exist; the exported name is `…_bytesinpersec_total`. A pattern with an alternation exported **nothing**; the prefix pattern works. | the data meters were empty for three runs | names fixed; allow list uses the prefix pattern. The agent now logs, once per pod, when a configured metric is missing. |
| `kubectl port-forward` to the gateway exits ("lost connection to pod") when its connection breaks; the connect scenario then failed for 15 minutes. | full run after the first M5 commit | the relay is supervised. |
| The observe script restarted the agent without its secrets environment (so the agent stayed dead and nothing was metered); several `set -e` slips in the script. | observe | fixed. |
| **M2 binding guard race**: 2 of 12 concurrent hand-made bindings to the same dedicated node were allowed in one full-suite run. | e2e under CPU contention | the guard remembers bindings it allowed for 30 s; a unit test fails without the fix. |

## Decisions taken

- Strimzi's network policy generation is switched off for the whole cell; the platform owns every policy in a tenant namespace (default deny, same namespace, DNS, API server, gateway, metrics, operator).
- The canary is a host process in kind and a per-cell Deployment in production (design §17); it reads the platform user's password from the secret store, never from the database.
- The health verdict is deliberately conservative about *no data*: a cluster with no canary results is not judged (a canary that is down is its own alert, not an outage of every cluster). The cost is that a canary that stops while a cluster fails is not seen by this evaluator; that needs an alert on the canary's own heartbeat, which is not built.
- Thresholds: production 99 % over 5 minutes as in the design; the kind cell uses 95 % over 90 s because one failed round is 3 attempts of a short window.

## What is not done or not proven

1. **Not built from the observability design (ADR-0013):** Thanos / `remote_write`, `prom-label-proxy` and the tenant metrics API, Perses dashboards, Fluent Bit log shipping, Alertmanager routing. Only the cell Prometheus with rules and runbooks exists.
2. **No alert has been seen to fire on the cell.** The test shows the rules load, evaluate and do not fire when healthy; `promtool` checks syntax. Broker-down in particular is hard for `up == 0` because a deleted pod leaves service discovery; the cluster-health signal, not the Prometheus alert, is what was tested.
3. **`privatelink_bytes`** and billing adjustments are not built.
4. **`data_out_bytes` is recorded but not checked against a known amount of consumed data**, and `data_in_bytes` is checked only to lie between the payload and three times the payload (batch overhead is included in the counter). The accounting of counters is proven by the unit and envtest oracles, not by this bound.
5. **Only two complete metering intervals were compared with the timeline in the last run** (earlier runs compared four); the tolerance (two sampling periods plus 5 %) is loose by design: the script samples every 5 s, the agent every 10 s.
6. **Thresholds in kind are not the production ones** (above); the production values have only been exercised in envtest with a controllable clock.
7. **The canary runs as one process.** The three-replica, one-per-zone Deployment, leader election between replicas and the heartbeat alert are not built.
8. **Canary reconnection every 2 minutes** is a choice made after a failure; the cost on production clusters (one SCRAM/TLS handshake per minute per broker connection) was not measured.
9. **Evaluator blind spot:** see the third decision above.
10. **Cluster-wide partition limit** (carried from M3/M4): not built; the broker metrics now exist to base it on.
11. **Open from earlier milestones, still open:** OIDC for the tenant API (static dev tokens), tier migration (spike S-6, now folded into M6), `readOnlyRootFilesystem`, delete taking 120–180 s with an unexplained namespace-controller cause (one M5 run had 140 s with PVCs the last thing to go), whether the User Operator removes tenant-created ACLs, storage expansion on a real cell, node rotation.
12. The unexplained transient from M3/M4 (a per-broker name served a certificate lacking its SAN right after `ACTIVE`) **appeared once more**, in the canary's log, 9 minutes after creation in one run ("x509: certificate is valid for kc-…-brokers-0.kc-… not b0.…"). Still unexplained. The canary retried and recovered.

```bash
make test e2e check-alerts              # unit + envtest + promtool
go test -tags e2e -race ./internal/canary   # the canary against a real Kafka (docker)
make kind-up && deploy/kind/smoke.sh observe   # needs docker, kind, kubectl, helm, jq, openssl
```
