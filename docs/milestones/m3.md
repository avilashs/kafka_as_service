# M3: connectivity and authentication

**Status:** implemented and verified on a real cell (kind, real Strimzi 1.3.0, real Envoy Gateway, real Kafka clients) in CI. Gaps are listed honestly under [What is not done or not proven](#what-is-not-done-or-not-proven); the main ones are OIDC (still static dev tokens), the partition limit, and no crash tests for the new update workflow.

Acceptance (from the brief): *standard `kafka-console-producer`/`kafka-console-consumer`, the Admin API and transactions work through the public endpoints; tenant A cannot reach tenant B by network or by credentials.*

## Scope delivered

| Area | What exists |
|---|---|
| Public endpoint | Strimzi `tlsroute` listeners behind one Envoy Gateway; SNI passthrough, TLS ends at the brokers. SCRAM on 9094 (`bootstrap.…`, `b<N>.…`), mTLS on 9095 (`mtls-bootstrap.…`, `m<N>.…`), both advertised on port 443. |
| Per-cluster PKI | Each cluster has its own cluster CA and clients CA (Strimzi). `GET /v1/clusters/{id}/ca-certificate` returns the public CA (the agent reads it from the cell and reports it). One CA per cluster only (Q-3): no public-CA certificates yet. |
| SCRAM users | `/scram-users` (create, list, delete, rotate, credentials). 256-bit random passwords; stored only in the secret manager (OpenBao in CI), written by the agent into a Secret in the tenant namespace. The database holds references. |
| mTLS users | `/mtls-users` (create, list, delete, renew, certificate), ADR-0018: the tenant sends a CSR, the cell signs it with the clients CA, the platform decides subject `CN=<name>`. Private keys never reach the platform. |
| Update workflow | `UpdateCluster` (prepare → publish generation → wait Ready → finish) under the per-resource lock; a failed update returns the cluster to ACTIVE with the reason on the operation. |
| Authorization | `PlatformAuthorizer` (Java plugin, subclass of `StandardAuthorizer`), create-topic and alter-config policies, derived Kafka image (`deploy/images/kafka`). Tenants manage ACLs with `kafka-acls` over the public endpoint; they cannot reach broker-level operations. ADR-0010. |
| Pod hardening | Every operand pod renders `runAsNonRoot`, seccomp `RuntimeDefault`, no privilege escalation, all capabilities dropped; the admission policy enforces this. `readOnlyRootFilesystem` still deferred. |
| Network | Strimzi listeners carry `networkPolicyPeers` (external: the gateway's proxy pods only; internal: own namespace), so Strimzi's own generated policies no longer open the ports to all. The M1 `allow-gateway-ingress` policy selected the wrong namespace (the Gateway object's, not the Envoy data plane's); fixed. |
| Secrets | `secrets.Store`: file (tests), OpenBao KV v2 (contract-tested against a real OpenBao); AWS Secrets Manager in M6. |

## Decisions taken (all from the approved recommendations)

Q-3 per-cluster private CA only; Q-4 SCRAM and mTLS on separate ports; broker pods hardened now (restricted profile accepted by real Strimzi pods; `readOnlyRootFilesystem` still deferred); `get nodes` token accepted in brokers; Q-9 tenants manage ACLs through the Kafka Admin API.

## Findings that contradict or refine the design

- **Cluster-wide `Create` bypasses per-topic authorization** (found by the broker test). Admin profile changed (ADR-0010).
- **`ElectLeaders` for own topics cannot be allowed** with a single cluster `Alter`; design §15.1 corrected.
- **Strimzi creates topics outside the `__` namespace** (`strimzi.cruisecontrol.*`); policies now reserve `strimzi.`.
- Envoy Gateway runs its proxy pods in its own namespace, not the Gateway object's: a `NetworkPolicy` that selected the Gateway namespace would have blocked all client traffic.
- Strimzi advertises tlsroute hosts on port 443 regardless of the listener port (confirmed by the working clients).
- Kind's CNI (kindnet in kindest/node 1.34) **does enforce NetworkPolicy**: the positive and negative controls in the isolation checks both held.
- Kafka 4.3's `kafka-producer-perf-test` takes `bootstrap.servers` as a command property.

## What is not done or not proven

1. **Authentication of the tenant API is still static dev tokens.** OIDC was planned for M3 in a code comment and in the milestone list; it is not built. Everything tenant-scoped is tested against that stub only.
2. **Partition limit** (cached count in `CreateTopicPolicy`, `CreatePartitions` gate): not built. Policies bound one request only.
3. **No crash tests for `UpdateCluster`.** The create/delete workflows have SIGKILL tests at every activity boundary; the update workflow reuses the same patterns and has a fault point, but no test kills a worker mid-update. A failed update leaves the new spec in place as the desired state (the user stays in the spec while the operation reports FAILED).
4. **Rotation window.** The new password is readable through the credentials endpoint as soon as it is written, slightly before the cell accepts it.
5. **User Operator vs tenant-created ACLs over time:** unobserved beyond the few minutes of the CI run (spike S-7 remainder).
6. **Real DNS, a real load balancer, per-gateway connection limits, throughput:** none. The public path in CI is a port-forward and a relay. No performance claim is made.
7. **mTLS certificates cannot be revoked** before expiry (90 days) except by deleting the user; the agent can sign any certificate (ADR-0018).
8. **The credentials endpoint returns the password over the API** (TLS in production, plain HTTP in the dev setup). Intended (`GET …/credentials`), but it makes the API token the key to the cluster.
9. AWS Secrets Manager, `readOnlyRootFilesystem`, delete time (121–181 s in this run; the namespace-controller cause from M2 is still unexplained), PSA enforce level.
10. Java plugins are tested on Kafka 4.1.0 locally and 4.3.1 in CI; 4.3.0 (offered by the API) has no derived image in the kind cell, so rendering for it fails with a clear error there.
11. Skipped check: gateway proxy shell check (see above).
